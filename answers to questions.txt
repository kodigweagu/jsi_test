Question 1 - Briefly describe how you would approach designing and implementing a database to store your 
model.
Answer - 
I would use a document database like MongoDB because the data has no fixed schema. The only consistent
fields are communicationType and DateTime, while the rest of the payload varies per record. Each record
would be stored as a document in a records collection with an id hash, communicationType, time, and the
raw fields from the source file.

To support queries, I would add a compound index on communicationType + time for the /TimeFilter
endpoint and a unique index on id to avoid duplicate inserts when reloading data. I would also maintain
a types collection (reference counted) for fast /GetTypes lookups, and expose a /ReconcileTypes endpoint
to rebuild it if needed.

Question 2 - Describe an authentication strategy that could be added to the TimeFilter endpoint
Answer - 
I would secure the TimeFilter endpoint with JWT-based authentication. Clients log in with username and
password via /Login, receive a JWT, and include it in the Authorization header. JWT verification is
cheap and stateless, so each request only needs to validate signature, expiry, and the subject (sub).

For admin-only operations, I would check the is_admin flag on the user record. I would expose
/RegisterUser for admin users to create new users, but the first admin user would be manually inserted
into the database (with a bcrypt password hash and password_changed_at). This avoids shipping admin
credentials in code or environment variables.

Question 3 - Briefly describe a strategy for creating a CI-CD pipeline for the API created in earlier tasks.
Answer - 
Jenkins would be triggered by GitHub webhooks on PRs and merges to main. The pipeline stages would look
like this:

- Checkout the main branch from GitHub (or the PR branch for validation builds).
- Install dependencies.
- Lint the codebase.
- Run tests and enforce coverage (fail the build if coverage is below the target).
- Build a Docker image tagged with the commit SHA.
- Run vulnerability scans (image and dependencies).
- Push the image to the registry.

CD would then automatically deploy to staging and verify the release:

- Deploy to staging using Helm with the newly built image tag.
- Run smoke tests against staging (/health, /ready, and a small happy-path flow).

For production, use a canary rollout with the NGINX Ingress Controller:

- The Helm chart templates two Ingress resources: a stable Ingress and a canary Ingress.
- The canary Ingress has annotations like nginx.ingress.kubernetes.io/canary: "true" and
  nginx.ingress.kubernetes.io/canary-weight: "5" for the initial traffic split.
- Traffic weight is adjusted via helm upgrade --set canary.weight=... to shift traffic gradually.

To avoid a long-running Jenkins job, use a cron-triggered “canary updater” pipeline:

- On initial rollout, store the start time (Jenkins parameter, ConfigMap, or S3).
- The cron job runs periodically (for example every 6 hours), reads the start time, computes elapsed
  time, maps it to a target weight (5% → 25% → 50% → 75% → 100%), and applies it via Helm.
- Typically you stop at 50–100%, then promote stable and disable the canary Ingress.

Alerting and rollback:

- Integrate Prometheus/Grafana or CloudWatch to monitor error rates, latency, and health.
- Jenkins polls metrics during the canary window; if thresholds are exceeded, it rolls back and sends
  Slack/Email alerts.
